# Интеграция «Портал поставщиков» (zakupki.mos.ru) — дизайн

**Дата:** 13.09.2026. **Инициатор:** Николай. **Статус:** approved design, готов к `writing-plans`.

## 1. Цель

Добавить второй источник тендеров — котировочные сессии (КС) Портала поставщиков
города Москвы, официальный интеграционный API которого мы разведали 13.09.2026
(см. переписку сессии и `docs/filters_v2_discovery.md` для контекста первого
источника). Источник должен ловить по тем же 50 фильтрам company_id=57
(`filters_v2.yaml`, волна 1 уже применена в проде), не заводя параллельную
конфигурацию, и не должен быть виден другим компаниям сервиса — токен
принадлежит лично владельцу, не платформе.

Дополнительная, но обязательная цель: переиспользовать существующий пайплайн
(матчинг, дедуп, уведомления, «Взять в работу», карточку тендера) как есть —
не строить параллельную инфраструктуру.

## 2. Решения владельца (согласованы в диалоге 13.09.2026)

| № | Решение |
|---|---|
| 1 | Один и тот же набор 50 фильтров `filters_v2.yaml` (company_id=57) обслуживает оба источника — не заводим отдельную конфигурацию под Москву |
| 2 | Матчится и виден **только** company_id=57 — токен персональный, не платформенный ресурс |
| 3 | Маршрутизация уведомлений — та же, что и для zakupki.gov.ru-совпадений того же фильтра (владелец группы + групповой чат/тема); в карточке — явная пометка источника |
| 4 | Архитектура опроса — Approach A: один периодический запрос по окну публикации + локальный матчинг всеми 50 фильтрами (не запрос на каждый из 1266 ключевиков — см. разд. 3 почему) |
| 5 | Токен (`PP_TOKEN`) — постоянный продакшн-секрет в Railway, не разовый |
| 6 | Полное описание КС (для лучшего матчинга многословных фраз) — Фаза 2, не блокирует первую версию |

## 3. Найденные факты об API (разведка 13.09.2026)

- Официальная документация: `https://zakupki.mos.ru/public-api-access/ks-search`
  (человекочитаемая) и `https://api.zakupki.mos.ru/swagger/v2/swagger.json`
  (полная OpenAPI-схема, публично доступна).
- Реальный эндпоинт: `GET https://api.zakupki.mos.ru/api/v2/auction/public/Search`,
  один query-параметр `query` (JSON), заголовок `Authorization: Bearer <PP_TOKEN>`.
- `query.filter` — `SearchQueryFilterDto`: `name` (StringFilter:
  contains/startsWith/endsWith/**isInverted** — исключения родные, на уровне
  API), `customerName`, `customerInn`, `startPrice` (RangeFilter), `publishDate`
  /`endDate` (RangeFilter\<DateTime\>), `status` (enum list), `id`.
- `query.order`, `query.skip`, `query.take` — пагинация и сортировка на уровне
  API.
- Ответ (`SearchQueryListDto`): `status, company, name, federalLaw,
  conclusionReason, startPrice, beginDate, endDate, id`. **Описания КС в
  списке нет** — только название (см. решение №6).
- `api.zakupki.mos.ru` (в отличие от `zakupki.mos.ru`, документация на котором
  открылась в браузере без проблем) похоже тоже режет не-российские IP —
  проверено эмпирически: прямой `curl`/`urllib` зависают, `requests` через
  российский прокси (тот же пул, что и `PROXY_URL*` для zakupki.gov.ru) —
  проходит. Значит боевой опрос должен идти из worker-сервиса (там прокси уже
  настроен), не с произвольной машины.
- Почему не «запрос на каждый ключевик» (как для zakupki.gov.ru): 13.09.2026 в
  этой же сессии ровно такой подход по zakupki.gov.ru (1266 ключевиков) вызвал
  реальную деградацию прокси-пула (403/сброс соединений на несколько часов),
  задев боевой матчинг для всех компаний сервиса. Повторять это на новом
  источнике — неоправданный риск. Один периодический запрос по временному
  окну + локальный матчинг тем же `SmartMatcher` кардинально меньше нагружает
  прокси и переиспользует уже написанный, протестированный движок сопоставления.

## 4. Архитектура

### 4.1 Новые файлы

- `tender_sniper/sources/mos_portal_client.py` — HTTP-клиент: Bearer-авторизация,
  HTTP-сессия через тот же прокси-пул и ту же ретрай-логику по прокси
  (403/таймаут → следующий `PROXY_URL_N`), что уже реализована в
  `src/parsers/zakupki_rss_parser.py` (переиспользовать её приватную
  прокси-ротацию как есть, не копировать логику заново — либо вынести общий
  хелпер, либо параметризовать существующий класс; решить на этапе плана).
  Метод `search_auctions(publish_date_from, publish_date_to, skip=0,
  take=200) -> List[dict]` — вызывает `Search`, разворачивает пагинацию,
  возвращает сырые DTO.
- `tender_sniper/sources/mos_portal_mapper.py` — чистая функция
  `ks_dto_to_tender(dto: dict) -> dict`, реализующая таблицу маппинга полей
  разд. 4.2 ниже. Без сетевых вызовов — легко тестировать на fixture-JSON.
- `tender_sniper/jobs/mos_portal_poll.py` — фоновый цикл по образцу
  `tender_sniper/jobs/archive_lost_cards.py`/`expire_deadline_cards.py`:
  раз в `MOS_PORTAL_POLL_INTERVAL_SECONDS` (по умолчанию 600 — 10 минут)
  тянет новые КС за окно «с последнего успешного опроса минус 30 минут
  нахлёста» (нахлёст — подстраховка от неточности `publishDate` на стороне
  портала), прогоняет каждую через `ks_dto_to_tender`, затем через
  `SmartMatcher.match_tender()` по каждому активному фильтру company_id=57,
  для совпадений — тот же путь сохранения/уведомления, что и в
  `tender_sniper/service.py` (дедуп по `tender_number`, `save_notification`,
  `TelegramNotifier.send_tender_notification` с `notify_chat_ids`/
  `notify_thread_id` фильтра).
- Запускается в **worker**-сервисе (`SERVICE_ROLE=worker`,
  `tender_sniper/worker_main.py`) как ещё один `asyncio.create_task`, рядом с
  основным циклом `TenderSniperService` — не отдельный процесс/сервис.

### 4.2 Маппинг полей (KS DTO → tender-словарь SmartMatcher)

| tender-словарь | Источник |
|---|---|
| `number` | `"MOS-" + str(dto["id"])` — неймспейс исключает коллизии с числовыми номерами zakupki.gov.ru |
| `name` | `dto["name"]` |
| `description` | `""` (список КС описания не отдаёт — Фаза 2 может дотягивать через `ks-get`) |
| `price` | `dto["startPrice"]` |
| `region` | `"Москва"` (константа — портал по определению городской) |
| `customer_name` | `dto["company"]` |
| `published_date` | `dto["beginDate"]` |
| `submission_deadline` | `dto["endDate"]` |
| `url` | карточка КС на портале — точный шаблон уточнить по документации `ks-get` на этапе реализации (не найден в ходе разведки, только заглушка) |
| `source_label` | константа `"Портал поставщиков (Москва)"` — новое поле, не существовавшее в tender-словаре ранее (см. разд. 4.3) |

### 4.3 Пометка источника в карточке

`bot/formatters/tender_card.py::_build_text` — добавить необязательную строку с
`tender.get('source_label')`, если оно задано (для zakupki.gov.ru-тендеров
поле отсутствует — карточка выглядит как сейчас, без изменений). Один
опциональный `.get()`, обратной совместимости не нарушает.

### 4.4 Матчинг и дедуп

- Фильтры берутся напрямую из БД: `SELECT * FROM sniper_filters WHERE
  company_id = 57 AND is_active = true` — тот же набор, что worker уже
  использует для company 57 через `get_all_active_filters()`, просто с
  доп. условием `company_id = 57` (существующий метод не имеет такого
  параметра — нужен либо новый метод, либо фильтрация уже полученного
  списка на этапе job'а; решить в плане реализации).
- `SmartMatcher.match_tender(tender, filter_dict)` — вызывается как есть,
  никаких изменений в самом матчере не требуется (ё-нормализация и
  `keyword_wins_over_exclusion`, добавленные этой же сессией, уже
  подхватятся автоматически).
- Регион: у всех 50 фильтров `regions` включает `"Москва"` (это базовый
  регион во всех пресетах `filters_v2.yaml`) — ни один не отсеется по
  региону ошибочно.
- Дедуп: `is_tender_sent_to_chat(tender_number, chat_id)` и `sniper_notifications`
  работают по `tender_number` без изменений — `MOS-`-префикс не пересекается
  с форматом номеров zakupki.gov.ru (только цифры).

### 4.5 Credentials

- `PP_TOKEN` — новая переменная окружения, только в **worker**-сервисе
  (`miraculous-analysis`) — там, где реально идёт опрос. Хранить через
  `railway variables set --service miraculous-analysis` (не печатать значение
  в видимый вывод — тот же протокол, что уже соблюдался для `BOT_TOKEN`/
  `DATABASE_URL` этой сессией).
- При старте job'а — декодировать `exp` из JWT (без валидации подписи, только
  чтение claim) и залогировать warning, если до истечения < 30 дней. Токен
  сейчас истекает в 2036 — не проблема на годы вперёд, но проверка дешёвая и
  предотвращает молчаливый отказ в будущем.

## 5. Устойчивость и ошибки

- Прокси-ретрай — переиспользовать существующую ротацию `ZakupkiRSSParser`
  (пробовать `PROXY_URL`, `PROXY_URL_2`.. по очереди при 403/таймауте/ошибке
  соединения), не писать новую копию этой логики.
- Если ВСЕ прокси недоступны — залогировать и пропустить цикл (как уже делает
  основной мониторинг), не ронять worker целиком.
- Ошибка API (4xx/5xx, отличный от прокси-проблемы) — залогировать с телом
  ответа, пропустить цикл, продолжить со следующего интервала.
- Пагинация — ограничить разумным потолком страниц за один цикл (например,
  10 страниц по 200 записей = 2000 КС), чтобы аномальный всплеск публикаций
  не заблокировал цикл надолго; при достижении потолка — залогировать
  предупреждение (сигнал уменьшить интервал опроса или окно нахлёста).

## 6. Тестирование

1. Юнит-тест `ks_dto_to_tender()` на fixture-JSON (реальная форма ответа,
   зафиксированная в ходе разведки) — проверяет каждое поле маппинга.
2. Тест дедуп-неймспейсинга: `MOS-123` и `0123456789...` (числовой) никогда
   не считаются одним и тем же тендером.
3. Тест пометки источника: карточка с `source_label` показывает строку
   источника; карточка без него (обычный zakupki.gov.ru-тендер) — не
   показывает, выглядит как раньше.
4. Smoke-тест реального запроса к API (аналог `pp_probe.py`, но уже по
   найденному endpoint) — вручную, не часть автоматического CI (живой
   внешний сервис, требует прокси).

## 7. Вне рамок (сознательно не делаем сейчас)

  решение №6).
- Доступ других компаний сервиса к этому источнику (решение №2 — токен
  персональный).
- Запись КС Москвы в `tender_cache`/отдельный архив для бэктеста — не
  запрошено, не нужно для этой задачи.
- Обратная запись предложений/ставок в Портал поставщиков (API это умеет —
  `ChangeWinner`, `CreateShared` и т.п. — но это не тендерный мониторинг, а
  отдельная, более рискованная функциональность; не рассматривается).
