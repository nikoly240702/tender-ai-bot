# Аналитика ниш: что считаем и чему верить

Модуль отвечает на вопрос «стоит ли лезть в эту категорию»: сколько там
бывает участников, насколько роняют цену и не занята ли ниша одним
поставщиком. Источник — интеграционный сервис ЕИС, см.
[eis-data-source.md](eis-data-source.md).

## Как устроено

```
tender_sniper/sources/eis_integration.py   клиент сервиса ЕИС и разбор документов
tender_sniper/niche/storage.py             таблицы схемы eis, разбор в строки
tender_sniper/niche/ingest.py              загрузка (CLI)
tender_sniper/niche/metrics.py             индекс привлекательности
tender_sniper/niche/report.py              рейтинг и выгрузка (CLI)
scripts/verify_niche.py                    ручная сверка с карточкой ЕИС
```

Данные: схема `eis` — `procedure`, `protocol`, `contract`, `ingest_log`,
`okpd2_dict`. Метрики — материализованное представление
`eis.niche_metrics`, пересчёт после загрузки.

```bash
python -m tender_sniper.niche.ingest --region ЦФО --from 2026-08 --to 2026-09
python -m tender_sniper.niche.report --refresh --level 4 --region 77 --csv /tmp/n.csv
python -m scripts.verify_niche --purchase-number 0338300003326000140
```

## Срез и метрики

Срез = **код ОКПД2 (уровни 2/4/6) × регион × ценовая корзина**.
Корзины: `0-500k`, `500k-1m`, `1m-3m`, `3m-5m`.

| Метрика | Что означает |
|---|---|
| `procedures_count` | процедур в срезе |
| `median_bids` | медиана числа поданных заявок |
| `share_single_bid` | доля процедур с одной заявкой |
| `share_zero_bid` | доля процедур, куда никто не пришёл |
| `median_drop`, `p90_drop` | снижение цены: медиана и 90-й перцентиль |
| `median_nmck` | медиана НМЦК |
| `unique_winners`, `known_winners` | победителей всего и на скольких основана оценка |
| `comparable_prices` | на скольких процедурах посчитано снижение |
| `undefined_volume_count` | процедур с неопределённым объёмом (см. ниже) |
| `price_above_nmck_count` | процедур, где цена выше НМЦК |
| `monthly_trend` | помесячная динамика |

`winner_hhi`, `top3_winner_share`, `repeat_customers` считаются при
чтении из массивов ИНН: внутри одного `GROUP BY` долю от доли не
посчитать.

## Индекс привлекательности

Четыре составляющие, веса в `IndexConfig` (переопределяются
переменными окружения `NICHE_W_*`), **не в коде представления**.

```
C (конкуренция) = 100 * exp(-0.55 * (median_bids - 1))   1 заявка → 100, 3 → 33, 6 → 6
M (маржа)       = 100 * max(0, 1 - median_drop / 0.20)   0% → 100, 20%+ → 0
V (объём)       = 100 * min(1, ln(1+N) / ln(1+50))
O (открытость)  = 100 * (1 - min(1, HHI / 0.25))         HHI ≥ 0.25 → ниша схвачена

index = 0.35*C + 0.30*M + 0.20*V + 0.15*O
```

Срезы мельче пяти процедур выносятся отдельным списком «мало данных» —
в рейтинге они дают ложные вершины, но сама ниша может быть интересной.

### Допущения, без которых формула даёт бессмыслицу

Каждое закрыто тестом в `tests/unit/test_niche_metrics.py`.

1. **Ноль заявок не лучше одной.** Без ограничения снизу экспонента
   выдаёт 173 балла из 100. Ноль заявок — несостоявшаяся закупка.
2. **Отрицательное снижение не даёт маржи сверх 100%.**
3. **Нет данных о заявках — ноль баллов за конкуренцию,** а не свобода
   от конкурентов. Неизвестность не равна отсутствию.
4. **Победители неизвестны — ниша считается открытой.** По свежим
   срезам контракты ещё не заключены; штрафовать их не за что. Но это
   означает, что индекс таких срезов **завышен на 15 баллов**. Смотрите
   `known_winners`: если ноль — составляющая «открытость» не измерена.

## Ограничения данных — читать обязательно

### Неопределённый объём закупки

При неопределённом объёме (ч. 24 ст. 42 44-ФЗ) участники торгуются не
ценой контракта, а **суммой цен за единицу товара**. С НМЦК это
несопоставимо: встречались «победители» с 78 млрд против НМЦК в
1,45 млн, и среднее снижение по нишам уходило в минус тысячи процентов.

Такие процедуры помечены `quantity_undefined` и **исключены из метрик
снижения**, но остаются в подсчёте процедур и заявок — конкуренция в
них измеряется нормально. В Москве за полтора месяца их 22% потока.

### Открытый конкурс: цены в заявках нет

Победителя выбирают по критериям, и `applicationInfo` содержит только
состав заявки и решение о допуске. Цена берётся из
`rightConcludeContractPrice` — цены права заключить контракт.

### Победитель обезличен до контракта

В протоколе участник — это номер заявки. ИНН появляется только в
реестре контрактов, после заключения. Поэтому `winner_inn` в
`eis.protocol` всегда пуст, а HHI считается по `eis.contract`.
Следствие: **по свежим периодам концентрация не измеряется вовсе** —
контракт заключается позже протокола, и на коротком окне пересечения
почти нет.

### Лаг между документами

Извещение, протокол и контракт по одной закупке публикуются с разрывом
в недели. На выгрузке за один день пересечение между ними **нулевое**.
Для осмысленных метрик нужен период от нескольких месяцев, для
концентрации — от полугода.

### Снижение цены зависит от числа заявок

Замер по Москве (август–сентябрь 2026), после исключения процедур с
неопределённым объёмом:

```
1 заявка →  0,0%     нет конкуренции, цена остаётся на НМЦК
2        → 12,2%
3        → 25,6%
4        → 31,8%
5        → 40,1%
6        → 43,6%
```

Монотонность — основной признак того, что разбор верен. Если она
нарушится, чинить надо парсер, а не интерфейс.

## Известные слабые места

- **Вершина рейтинга вырождена.** У всех верхних ниш медиана заявок
  равна 1, из-за чего конкуренция и маржа дают по 100 баллов. Эти две
  составляющие (65% веса) измеряют по сути одно явление: при одной
  заявке снижения не бывает по определению. Индекс плохо различает
  ниши в верхней части.
- **`okpd2_primary` — самый частый код, а не код с наибольшей суммой**
  позиций, как в ТЗ: сумм по позициям в извещении нет. Расхождение
  возможно там, где одна дорогая позиция соседствует с множеством
  дешёвых; такие случаи видны по `okpd2_codes`.
- **223-ФЗ не загружается** — по ТЗ это второй этап.
