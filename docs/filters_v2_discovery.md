## 1. Где физически хранятся фильтры

Одна таблица, `sniper_filters` (`database.py:129+`), без отдельных таблиц под ключевики/исключения/регионы — всё лежит прямо в JSON-колонках строки фильтра:

- `keywords`, `exclude_keywords`, `regions`, `tender_types`, `customer_types` — JSON-массивы.
- `price_min` / `price_max` — числовые колонки.
- `tender_types` — это и есть текущий аналог `object_type` из ТЗ (значения вроде `['товары']`), но матчер его **не блокирует** (см. п. 2).
- `is_active` — булево, статуса `staged`/`archived` не существует.
- `company_id` — nullable FK на `companies` (добавлен в этом воркспейсе миграцией `20260910_multi_workspace`).
- `notify_chat_ids` (JSON, список Telegram chat_id) + `notify_thread_id` (int, добавлен сегодня же для тем/топиков) — маршрутизация уведомлений, см. п. 4.
- Также существуют, но **не читаются матчером вообще** (проверено grep'ом по `smart_matcher.py` — ноль обращений): `customer_keywords`, `okpd2_codes`, `excluded_customer_inns`, `excluded_customer_keywords`, `search_in`, `primary_keywords`, `secondary_keywords`. Это «Phase 2»-колонки из старой миграции, физически существуют, но мертвы для матчинга — не полагаться на них.

Нет уникального ключа кроме `id` — п. 3.

## 2. Как работает функция сопоставления

Файл `tender_sniper/matching/smart_matcher.py`, ядро — `_match_tender_internal` (∼888–1216). Важно: **ни одно из требуемых ТЗ правил матчинга (§4.2) сегодня не реализовано полностью**, кроме нижнего регистра. Это значит Этап 1–2 — не только загрузчик конфига, но и правки самого матчера.

- **Способ сравнения** — не ILIKE/полнотекст, а регэксп с кэшем компиляции: `_word_boundary_match` (686–701) строит `\b` + `re.escape(keyword)` и ищет `re.IGNORECASE`.
- **Границы слова — есть, но асимметричные, не то, что описано в ТЗ**: для ключевика **< 4 символов** — граница с обеих сторон (`\bкт\b`) — короткие ключевики типа «мдф», «узо», «тэн» защищены полностью. Для ключевика **≥ 4 символов** — граница ТОЛЬКО слева (`\bкабель` совпадёт и с «кабельный», и с «кабелем» — это осознанный дизайн для словоформ). Следствие: пример из ТЗ «кран не должен совпадать с экран» и «мат — с формат» **уже сегодня работают верно** (в обоих случаях нет левой границы перед искомым словом внутри большего слова) — но это скорее счастливое совпадение примеров, чем гарантия: полноценной **правой** границы для ключевиков ≥4 симв. нет вообще, то есть «дом» (тоже <4, защищён) — ок, а вот более длинный ключевик может «съесть» суффикс совсем другого слова, если тот начинается ровно с этой подстроки после границы. Нужно явно решить с Николаем: оставляем как есть (стемминг-дизайн) или добавляем режим «строго целое слово» по флагу.
- **ё/е — подтверждено, нормализации НЕТ нигде** ни в матчере, ни в парсерах (грепал `ё`→`е` таблицы, `unicodedata.normalize`, `str.translate` — ноль совпадений в реальном пути сопоставления). Есть модуль `tender_sniper/morphology.py` с лемматизацией (pymorphy2), но он **не импортируется** в `smart_matcher.py` — то есть готовый инструмент есть, просто не подключён. `defaults.matching.normalize_yo: true` из YAML — целиком предстоит реализовать.
- **Многословные ключевики — подтверждена AND-логика без учёта порядка/соседства**: `_match_compound_phrase` (739–770) режет фразу на слова (кроме стоп-слов) и требует, чтобы КАЖДОЕ слово фразы нашлось где-то в объединённом `name + description` — не обязательно рядом. Работает одинаково для 2 и для 5+ слов (единый код путь). Это ТОТ ЖЕ корень, что и разбор 06-16 про «аппарат КТ» — учтено в v2 отказом от таких генериков, но сам движок не изменился.
- **Исключения — принципиально другая логика, и `keyword_wins_over_exclusion` сегодня НЕ существует вообще, ни частично**. Исключения проверяются в отдельном блоке ДО подсчёта скора по ключевикам (925–953) через тот же `_word_boundary_match`, но **как целая строка** — не через AND-по-словам, как позитивные ключевики. Как только исключение находится — `return None` немедленно, без проверки, не является ли оно частью только что найденного ключевика. Это 100% новая логика, которую нужно написать с нуля.
- **Какие поля тендера ищутся** — `searchable_text = f"{tender_name} {tender_description}"` (904–923), где `tender_description` — это `description` с фолбэком на `summary`. Это единственная строка, где ищутся и ключевики, и исключения. `customer_name` явно **исключён из поиска нарочно** (комментарий в коде: иначе «УПРАВЛЕНИЕ ЛОГИСТИКИ» матчило бы все тендеры этого заказчика). ⚠️ **YAML требует `search_fields: ["наименование объекта закупки", "наименования позиций (спецификация)"]` — позиций спецификации в этом блоке физически нет.** Есть отдельный, тяжёлый AI-модуль (`tender_sniper/ai_document_extractor.py`) для извлечения позиций из скачанных документов тендера через GPT-4o — но это ручной, по-документный анализ по клику «AI-анализ» в карточке, а не то, что можно прогнать по каждому входящему тендеру на потоке мониторинга. Реализовать поиск по позициям спецификации в реальном времени — отдельная, вероятно немаленькая задача (нужно either вытаскивать позиции по каждому тендеру дёшево на входе, either смириться с тем, что v2 матчится только по названию+описанию). **Это открытый вопрос ниже, а не решение, принятое молча.**
- **Слэш в ключевике — подтверждено, ровно как в ТЗ**: `/` не эскейпится и не используется как OR-разделитель нигде в коде (ни в матчере, ни в хендлерах создания фильтра). `"частотный преобразователь/преобразователь"` после разбивки по пробелам даёт AND-слово `"преобразователь/преобразователь"` со слэшем внутри регэкспа — практически никогда не встретится в реальном тексте тендера. Валидатор `filters_v2.yaml` уже запрещает `/` — это закрывает проблему на уровне конфига, но сам движок слэши не глотает.
- **Регионы** — отдельная, куда более развитая логика, чем у ключевиков: `_check_region_match` (566–656), нечёткое каскадное сравнение (точное совпадение → нормализация суффиксов «область»/«край»/«республика» → подстрока в обе стороны → алиасы вроде «спб»↔«санкт-петербург»). Пустой/неизвестный регион тендера при непустом списке регионов фильтра — жёсткий отказ (без бэкдора). Так что «пустой список регионов = вся РФ» — это баг именно в данных (пустой JSON-массив), а не в логике сравнения; логика сама по себе региона без региона не пропустит.
- **`tender_types`/`object_type` — не блокирует сегодня.** Есть закомментированный `return None` (∼988–991) — несовпадение типа логируется, но тендер не отклоняется. Явное требование ТЗ «`object_type` обязателен» потребует раскомментировать/дописать эту проверку — сейчас это чисто косметическое поле.

**Тесты**: `tests/unit/test_smart_matcher.py` — 34 прошли / 8 упали (воспроизвёл сам: `pytest tests/unit/test_smart_matcher.py -q` → `8 failed, 34 passed`). Упавшие — не про новый функционал, а про то, что тесты писались до ужесточения регионной логики и до правила «0 совпавших ключевиков → `None`»: тесты ожидают старое, нестрогое поведение. Полезная страховка есть только для: word-boundary, регистронезависимости, exclude-механики (как есть, без keyword_wins), цен, скоринга, batch-матчинга. Про ё, слэш, keyword_wins_over_exclusion, Phase-2-поля — тестов нет вообще (что логично — там и функционала нет).

## 3. Уникальные ключи для upsert

Подтверждено — только `id` (автоинкремент). Ни `UniqueConstraint`, ни индекса по `name`, ни `slug` — нигде, ни в `database.py`, ни в истории миграций. Ровно то, что предполагает ТЗ: нужна миграция, добавляющая `slug UNIQUE`.

## 4. Связь фильтра с получателем уведомлений

Уже реализовано и вполне достаточно для задачи — отдельного изобретения не требуется:

- `notify_chat_ids` (JSON-список Telegram chat_id; пусто → фолбэк на личку владельца фильтра) + `notify_thread_id` (int, тема супергруппы — добавлено сегодня в этом же воркспейсе для темы «Уведомления от бота»).
- В `filters_v2.yaml` у каждой группы уже есть `owner: nikolai | artem` — прямое соответствие: у артёмовских групп (`build_goods`, `build_works`, `tools`) `notify_chat_ids` = [телеграм-id Артёма, id группы], у остальных — [телеграм-id Николая, id группы], `notify_thread_id` = 230 у всех (текущая тема). Это чисто данные, никакого нового кода не нужно.
- **Подписок/дайджеста в системе нет вообще.** Проверено — нигде в репо нет `APScheduler`/`schedule.every`/`croniter`/`add_job` — ни одного планировщика задач кроме двух уже существующих `while True: sleep(N)`-циклов (архивация pipeline, автопросрочка дедлайнов). «Раздельный дневной дайджест» по группам (Этап 6, второе предложение) — это НЕ доработка, а новая инфраструктура с нуля. ТЗ сам разрешает вынести это отдельно («если не поддерживается — не изобретать») — рекомендую этим и ограничиться в рамках текущей задачи: только прямая маршрутизация per-filter, без дайджеста.

## 5. История совпадений и её пригодность для бэктеста (Этап 4)

Три отдельные находки, вместе дающие однозначный вывод:

1. **`match_count` ≠ количество строк `sniper_notifications`.** Счётчик на фильтре инкрементится ТОЛЬКО при реально сохранённом уведомлении (`sqlalchemy_adapter.py:1023`, внутри `save_notification`) — но `sniper_notifications` физически пуст почти целиком: сейчас в таблице 762 строки на весь продукт (все компании), из них у компании 57 — **140 строк, все за последние ~3 дня**. Это не баг и не скрытая потеря данных — это последствие моих же собственных действий этой сессией (удаление компании 1 стёрло её 6647 уведомлений). Но для company 57 конкретно это означает: реальной истории уведомлений для бэктеста 50 новых фильтров практически нет, а то, что есть — отражает СТАРЫЕ 17 фильтров, не новые 50.
2. **`tender_cache` — не архив, а таблица дедупликации, физически пустая.** Схема — только `tender_number`, `tender_hash` (MD5), `first_seen`/`last_seen`, `times_matched` (`database.py:253-262`) — ни названия, ни цены, ни региона тендера там нет и никогда не было. Более того: ни один код в репозитории не вызывает функции записи в неё (`mark_tender_processed`) — похоже, таблица вообще не используется в текущем пайплайне (реальная дедупликация отправки идёт через `is_tender_sent_to_chat` по `sniper_notifications`). Как источник «сырого потока тендеров за 30 дней» — не подходит категорически.
3. **Нет автоматической очистки `sniper_notifications`** (грепал по всему репо scheduler-примитивы — их нет вообще) — только ручная кнопка «очистить историю» в Telegram, per-user. То есть если бы не моя собственная чистка компании 1, история была бы длиннее — но структурно она всё равно отражала бы только СТАРЫЕ фильтры, не новые 50.

**Вывод: бэктест «прогнать новый конфиг по нашему архиву» в буквальном виде невозможен — архива нет.** Но ТЗ сам предусматривает запасной путь («если истории нет — собрать выгрузку из источника»), и он реально существует в коде: `tender_sniper/instant_search.py` умеет искать **непосредственно на zakupki.gov.ru**, включая режим `purchase_stage="archive"` (∼482-536) — client-side фильтр, оставляющий только тендеры с уже прошедшим дедлайном подачи, то есть реальный архив источника, а не наш локальный. Это и есть механизм для Этапа 4: прогнать каждый из 50 новых фильтров через `InstantSearch.search_by_filter(..., purchase_stage="archive")` напрямую по зактупкам, а не по нашей БД.

**Открытый вопрос**, который я не смог закрыть чтением кода: не нашёл, можно ли гарантированно ограничить это окном именно «последние 30 дней» для каждого фильтра — в файле есть параметр `date_from` (∼182), но с других участков кода, с дефолтом «сегодня минус 3 дня» для другого сценария (обычный мониторинг, не архивный поиск). Нужно либо проверить эмпирически, на сколько глубоко в прошлое реально отдаёт архивный поиск zakupki.gov.ru, либо явно решить с Николаем ограничиться тем окном, что реально доступно, и не тянуть время на подгонку под ровно 30 дней.

## 6. Что происходит при удалении фильтра

Проверено на боевой БД (`pg_constraint.confdeltype`):

| Таблица | При удалении фильтра |
|---|---|
| `sniper_notifications`, `search_history`, `user_feedback`, `ai_feedback` | `filter_id` → `NULL` (строки остаются, просто теряют привязку) |
| `pipeline_cards` | **`NO ACTION`** — если у фильтра есть хоть одна карточка в пайплайне, `DELETE` целиком блокируется ошибкой FK |

То есть физическое удаление сегодня и так небезопасно и непредсказуемо (сработает или нет — зависит от случайного наличия карточек), а не просто «нежелательно по регламенту». Требование ТЗ «архивировать, не удалять» — единственный вариант, который вообще гарантированно работает при любом состоянии данных.

## Итоговый список открытых вопросов Николаю
