# Real-time синк Bitrix24 → Pipeline (кабинет) — Design Spec

**Дата:** 2026-08-27
**Автор:** Николай Чижик (с агентом)
**Статус:** Draft, ожидает финального ревью

---

## 1. Цель и контекст

### Что строим

Подпроект №1 из плана «довести кабинет-канбан до полного паритета с Bitrix24, а лучше» (см. переписку — декомпозиция на 5 подпроектов). Это фундамент: без него остальные фичи (несколько воронок, задачи, bulk-действия, автоматизация по стадиям) будут смотреть на неполные/устаревшие данные.

### Зачем

Bitrix24 остаётся основной площадкой команды (текущий бизнес-партнёр Николая ненадёжен — не выполняет обязательства, задерживает деньги, находится в процессе банкротства). Николай параллелит работу с другой командой и хочет, чтобы кабинет стал **живым зеркалом** всего происходящего в Bitrix — чтобы в перспективе можно было безболезненно полностью уйти с Bitrix, не потеряв ни одного действия по пути.

Сегодня синк Bitrix → Pipeline (см. `cabinet/bitrix_sync.py`) сильно неполный:
- Опрос раз в 5 минут (`tender_sniper/jobs/bitrix_pull_sync.py`), а не событийно.
- Распознаёт только 4 стадии сделки из полной воронки (`_PULL_STAGE_MAP`: NEW / AI-стадия / WON / LOSE) — промежуточные стадии в Bitrix не долетают вообще.
- Комментарии, лента событий, изменения полей (сумма, заказчик, срок, ответственный) в обратную сторону не синкаются в принципе.
- Удаление сделки в Bitrix никак не отражается в кабинете.

Push в обратную сторону (Pipeline → Bitrix, `push_card_created` / `push_stage_changed` / `push_result_set` / `push_assignee_changed`) уже работает нормально и не меняется в этом подпроекте.

### Цели

1. Изменения стадии / создание / удаление сделки в Bitrix отражаются в Pipeline **за секунды**, а не за 5 минут.
2. Изменения ключевых полей сделки в Bitrix (название, сумма, заказчик, регион, срок, ответственный) видны в истории карточки.
3. Комментарии из ленты сделки в Bitrix попадают в историю карточки (задержка до ~2 минут допустима — у Bitrix нет push-события на комментарий).
4. Ничего не теряется даже при сбое доставки вебхука (сетка безопасности).
5. Удаление сделки в Bitrix не удаляет данные безвозвратно — карточка архивируется.

### Non-goals (не в этом подпроекте)

- Несколько воронок/досок, задачи/напоминания, bulk-действия, автоматизация по стадиям — отдельные подпроекты (2-5 по декомпозиции).
- Полноценное Bitrix-приложение с OAuth (`event.bind`) — избыточно для системы, с которой планируется уйти. Используем портал-конфигурируемый «исходящий вебхук» (без OAuth).
- Синк файлов, прикреплённых к сделке в Bitrix (пользователь не отметил это критичным сейчас).
- Изменение направления Pipeline → Bitrix (уже работает).
- Перезапись `sale_price`/`purchase_price` из Bitrix `OPPORTUNITY` — это независимый ручной расчёт маржи в кабинете, трогать не будем.
- Обратное сопоставление ответственного, если в Bitrix назначен человек без аккаунта в кабинете, — просто показываем имя текстом, без попытки привязать к несуществующему `sniper_users`.

## 2. Архитектура

### Компоненты

```
Bitrix24 (портал команды)
   │
   │ 1. «Исходящий вебхук» (настраивается руками в Bitrix UI,
   │    без OAuth-приложения) — на события:
   │    OnCrmDealAdd / OnCrmDealUpdate / OnCrmDealDelete / OnCrmDealMoveToCategory
   ▼
POST /webhook/bitrix24/events?c=<company_id>&t=<secret>
   │  (новый aiohttp-хендлер, по образцу /webhook/bitrix24/analyze)
   │  — проверяет secret, отвечает 200 сразу, дальше — fire-and-forget
   ▼
cabinet/bitrix_sync.py :: handle_deal_event(company_id, event, deal_id)
   │  — НЕ доверяет телу запроса Bitrix (там только ID), заново
   │    запрашивает актуальные данные через СВОЙ сохранённый
   │    входящий вебхук компании (crm.deal.get)
   ├─ ADD/UPDATE/MOVETOCATEGORY → upsert карточки + diff полей → история
   └─ DELETE → архивация карточки (не hard delete) → история

Параллельно, независимо от событий:

tender_sniper/jobs/bitrix_comment_sync.py (новый, интервал ~90 сек)
   │  — т.к. у Bitrix нет push-события на добавление комментария
   │  — проходит по карточкам компании с bitrix_deal_id,
   │    батчем (Bitrix `batch` method, до 50 подзапросов) вызывает
   │    crm.timeline.comment.list(ENTITY_ID=X, filter[>ID]=last_seen)
   ▼
   новые комментарии → история карточки

tender_sniper/jobs/bitrix_pull_sync.py (существующий, интервал снижается
   с 5 мин до 1 часа) — сетка безопасности на случай недоставленного
   вебхука. Логика не меняется, меняется только частота.
```

### Почему не `event.bind` / OAuth-приложение

`event.bind` работает только в контексте OAuth-авторизованного приложения — обычный входящий вебхук (то, что уже настроено у пользователя) для подписки на события не подходит. Поднимать полноценное Bitrix-приложение (OAuth install flow, client_id/secret, refresh-токены) — несоразмерные трудозатраты ради системы, которую планируется покинуть. «Исходящий вебхук» даёт push-события за один клик в UI Bitrix, без кода на стороне Bitrix-приложения.

### Почему не «просто ускорить поллинг»

Рассматривался вариант B («тот же поллинг, но раз в 30-60 сек и по всем полям»). Отклонён: задержка всё равно ограничена снизу интервалом опроса, а частый опрос **всех** сделок компании (а не только изменившихся) создаёт ненужную нагрузку на Bitrix REST API без событийной точности («что именно изменилось»). Событийная модель даёт секундную задержку почти бесплатно.

### Безопасность инбаунд-эндпоинта

Тело запроса от Bitrix содержит только `event` и `ID` сделки — этого недостаточно и не нужно доверять напрямую. Схема:
1. У каждой компании — свой сгенерированный `bitrix_inbound_secret` (аналогично `bitrix24_webhook_url`, хранится в `data` владельца компании).
2. URL для настройки в Bitrix содержит `company_id` + `secret` как query-параметры — Bitrix зовёт ровно этот URL.
3. Хендлер сверяет `secret` с сохранённым для `company_id`, иначе 401.
4. Данные для апдейта карточки **всегда** берутся через `crm.deal.get`/`crm.timeline.comment.list` с использованием собственного webhook компании — то есть даже если бы кто-то подделал вызов на `/webhook/bitrix24/events`, максимум что он может — спровоцировать пересчёт реальных данных по реальной сделке этой же компании, а не подсунуть произвольные данные.

## 3. Данные и модель

### Новые поля (в `data` JSON, без миграции схемы)

- `SniperUser.data['bitrix_inbound_secret']` (у владельца компании, рядом с `bitrix24_webhook_url`) — генерируется при первом заходе в раздел настроек синка, `secrets.token_urlsafe(24)`.
- `PipelineCard.data['bitrix_snapshot']` — dict последних известных значений отслеживаемых полей Bitrix-сделки (`TITLE`, `OPPORTUNITY`, `UF_CRM_TENDER_CUSTOMER`, `UF_CRM_TENDER_REGION`, `CLOSEDATE`, `ASSIGNED_BY_ID`, `STAGE_ID`) — используется для diff при каждом событии.
- `PipelineCard.data['bitrix_last_comment_id']` — курсор для поллинга комментариев.
- `PipelineCard.data['bitrix_assigned_name']` — человекочитаемое имя ответственного в Bitrix, если он не сопоставлен ни с одним `sniper_users` (для отображения на карточке).

Новых таблиц не требуется — история пишется в существующую `PipelineCardHistory` с новыми значениями `action`:
- `bitrix_field_changed` — payload `{field, old, new}` (одна запись на одно изменённое поле за событие).
- `bitrix_comment` — payload `{author, text, created}`.
- `bitrix_deal_deleted` — payload `{bitrix_deal_id}`.
- `card_created_from_bitrix` — payload `{bitrix_deal_id}` (событийный аналог существующего `imported_from_bitrix`, для случая когда сделка появилась в Bitrix напрямую, а не через наш push).

### Переиспользуемая логика

`import_deals_to_pipeline` в `cabinet/bitrix_sync.py` уже содержит логику «сборка `card_data` из одного `deal` от Bitrix». Выносим общую часть в `_upsert_card_from_deal(company_id, deal, source)`, которую используют и bulk-импорт, и `handle_deal_event`, — чтобы не дублировать маппинг полей.

Существующие `_STAGE_ORDER` (anti-rollback) и `_PULL_STAGE_MAP` переиспользуются как есть внутри `handle_deal_event` для обработки `STAGE_ID`.

## 4. Обработка событий по типам

- **`ONCRMDEALADD`**: если карточки с таким `bitrix_deal_id` ещё нет — создать через `_upsert_card_from_deal(source='bitrix_event')`, история `card_created_from_bitrix`.
- **`ONCRMDEALUPDATE`** / **`ONCRMDEALMOVETOCATEGORY`**: найти карточку по `bitrix_deal_id` (если нет — создать, как при ADD, на случай пропущенного события создания). Сравнить свежие поля со `bitrix_snapshot`, для каждого изменённого поля — отдельная запись `bitrix_field_changed`. `STAGE_ID` — через существующую anti-rollback логику (если в Pipeline карточка уже дальше по стадиям, откат не делаем — Pipeline остаётся источником истины для прогресса вперёд, как и сейчас).
- **`ONCRMDEALDELETE`**: найти карточку по `bitrix_deal_id`, если найдена — `archived_at = now()`, история `bitrix_deal_deleted`. Если карточки нет — no-op.
- **Ответственный (`ASSIGNED_BY_ID`)**: попытаться найти `sniper_users` с `data['bitrix_user_id'] == ASSIGNED_BY_ID` этой же компании. Если найден — обновить `assignee_user_id` (плюс `bitrix_field_changed`). Если не найден — не трогать `assignee_user_id` (FK-целостность), только обновить `data['bitrix_assigned_name']` и залогировать `bitrix_field_changed` с текстовым значением.

---

## 5. Комментарии (поллинг)

Bitrix не даёt событие на добавление комментария и не даёt способ получить «новые комментарии по всем сделкам компании одним запросом» — `crm.timeline.comment.list` требует конкретный `ENTITY_ID`. Поэтому:

- Новый фоновый job, интервал 90 сек, аналог `bitrix_pull_sync.py` по структуре.
- Для каждой компании с настроенным входящим вебхуком — берёт активные (не архивные) карточки с `bitrix_deal_id`.
- Батчит запросы через Bitrix `batch` (до 50 подзапросов за один HTTP-вызов) — при паре сотен карточек это единицы запросов за цикл, не нагружает Bitrix REST.
- Для каждой сделки: `crm.timeline.comment.list(filter={ENTITY_ID, ENTITY_TYPE: 'deal', '>ID': last_seen})`, новые — в историю карточки (`bitrix_comment`), обновить `bitrix_last_comment_id` на максимальный `ID` из полученных.
- При нуле карточек с `bitrix_deal_id` у компании — цикл для неё пропускается (нет смысла дёргать API).

## 6. UI

Новых вкладок не создаём — вкладка «История» у карточки (`renderHistory`/`formatHistoryAction` в `cabinet/static/js/pages/pipeline.js`) уже существует. Расширяем `formatHistoryAction` новыми типами:
- `bitrix_field_changed` → `«Название» изменено в Bitrix: «А» → «Б»` (или для суммы — с форматированием как в `fmtPrice`).
- `bitrix_comment` → `💬 {author} (Bitrix): {text}`.
- `bitrix_deal_deleted` → `🗑 Сделка удалена в Bitrix — карточка перенесена в архив`.
- `card_created_from_bitrix` → `➕ Карточка создана из Bitrix (сделка #{id})`.

На странице Настроек (`cabinet/templates/settings.html`, там же где сейчас настраивается `bitrix24_webhook_url`) — новый блок «Обратный синк из Bitrix»: показывает сгенерированный URL для исходящего вебхука + инструкцию (куда в Bitrix его вставить, какие 4 события отметить), кнопку «Сгенерировать заново» (ротация секрета — на случай утечки).

## 7. Обработка ошибок

Сохраняем принцип, уже задокументированный в `bitrix_sync.py`: интеграция с Bitrix — best-effort, её сбои не должны ронять кабинет. Все новые функции — `try/except` с логированием, как и существующие `push_*`/`pull_*`. Инбаунд-хендлер отвечает Bitrix 200 максимально быстро (до какой-либо реальной обработки), обработка — в фоновой задаче (`fire_and_forget`, уже есть в файле).

## 8. Тестирование

- `handle_deal_event` для всех 4 событий (ADD/UPDATE/MOVETOCATEGORY/DELETE), с моком `crm.deal.get` — новая карточка создаётся, существующая обновляется, поля диффятся корректно, удалённая архивируется.
- Anti-rollback: событие с более ранней стадией не откатывает карточку, ушедшую вперёд по Pipeline.
- Секрет: неверный/отсутствующий `t` → 401, эндпоинт не создаёт фоновую задачу.
- `_upsert_card_from_deal` покрыт существующими тестами импорта (уже есть для `import_deals_to_pipeline`) плюс новый путь `source='bitrix_event'`.
- Комментарий-джоб: мок `batch`-ответа, проверка что `bitrix_last_comment_id` продвигается и повторный прогон не создаёт дублей в истории.
- Ответственный без сопоставления в `sniper_users` → `assignee_user_id` не трогается, `bitrix_assigned_name` обновляется.

## 9. Открытые вопросы (не блокируют старт, но стоит держать в уме)

- Партнёр может не согласиться / не суметь настроить исходящий вебхук в Bitrix (нужны права администратора портала). Если доступа нет — весь подпроект деградирует до текущего почасового поллинга (сетка безопасности), что не хуже статус-кво.
- Формат `auth[application_token]`, который Bitrix кладёт в тело исходящего вебхука, можно дополнительно сверять как второй фактор (в доке Bitrix упоминается) — не обязателен при выбранной схеме (secret в URL + refetch через свой webhook), но дёшево добавить как doubly-safe проверку на этапе реализации.
