# Генератор коммерческих предложений (КП) — дизайн

**Дата:** 2026-07-17
**Статус:** дизайн на ревью
**Автор:** Claude + Николай

## 1. Цель

Дать пользователю в Telegram быстро собирать коммерческое предложение (КП):
он вводит позиции (наименование, кол-во, цена), система нумерует, считает суммы
и итог, подставляет реквизиты продавца и отдаёт готовый **PDF** в строго
фиксированном фирменном шаблоне. Убирает ручную сборку КП в Excel/1С.

Не путать с существующим `tender_sniper/document_generator/` — тот генерит **пакет
заявки на тендер** (заявка/декларация/договор/техпредложение) в DOCX. КП — это
отдельный **коммерческий прайс-документ**.

## 2. Ключевые решения (согласованы)

| Вопрос | Решение |
|---|---|
| Где живёт | **Telegram** (команда живёт в Bitrix, веб-кабинетом не пользуются) |
| Ввод позиций | **Последовательный по полям** (наименование → предлагаемое наименование → ед.изм → кол-во → цена), с **предпросмотром** перед генерацией |
| Парсинг | **Детерминированный** (без AI): цена — деньги, ошибка недопустима |
| Колонки имени | Спрашиваем **обе**: «Наименование» и «Предлагаемое наименование» |
| НДС | Toggle: **без НДС (УСН, дефолт)** / **с НДС 20%** (задел под будущее ООО) |
| PDF-движок | **WeasyPrint** (HTML+CSS → PDF, точное попадание в бланк) |
| Реквизиты продавца | Переиспользуем существующую модель `CompanyProfile` |

## 3. Шаблон (по образцам ИП Хисамеева)

**Шапка (слева):** наименование продавца, ИНН/КПП, адрес, телефон, email.
**Шапка (справа):** метки `Куда:` / `Тел.:` / `Кому:` — заполняются получателем (могут быть пустыми).
**Заголовок (центр):** `КОММЕРЧЕСКОЕ ПРЕДЛОЖЕНИЕ № {префикс}-{номер}` (напр. `ИПХИС-26063`).

**Таблица позиций** (колонки строго в этом порядке):
`№` · `Наименование` · `Предлагаемое наименование` · `Ед. изм.` · `Кол-во` ·
`Цена за ед., RUB без НДС` · `Сумма, RUB без НДС` · `Срок поставки`.

**Строка итога:** `Всего без НДС: {сумма}` (в режиме НДС — `Итого: … / в т.ч. НДС 20%: …`).

**Подвал:**
- `Срок действия данного предложения {N} календарных дней.`
- `Условия оплаты: {текст}`
- `Условия доставки: {текст}`
- `Цены действительны при полном объеме закупки. Срок поставки указан без учета праздничных выходных.`
- разделительная линия
- `С наилучшими пожеланиями,` / `{ФИО подписанта}`

**Что фиксировано** (из `CompanyProfile` / дефолтов): шапка продавца, подпись,
тексты условий, срок действия.
**Что вводится на каждый КП:** получатель, режим НДС, позиции, срок поставки.
**Что авто:** № КП, нумерация строк, Сумма = Кол-во × Цена, Итого, НДС-разбивка.

## 4. Поток в Telegram (FSM)

Реализуется как aiogram FSM (по образцу существующего `bot/handlers/company_profile.py`).

```
/kp  (или кнопка «Сформировать КП»)
  0. Проверка: заполнен ли CompanyProfile. Нет → предложить /profile.
  1. Получатель: Куда / Кому / Тел  (кнопка «Пропустить» → пустые метки)
  2. Режим НДС:  [без НДС (УСН)]  /  [с НДС 20%]     (дефолт — без НДС)
  3. Срок поставки (общий для КП):  ввод или дефолт («По заявкам» / «15 к.д.»)
  4. Цикл добавления позиций — на КАЖДУЮ позицию по шагам:
        a. Наименование
        b. Предлагаемое наименование
        c. Ед. изм.  (быстрые кнопки: шт. / упак. / кг / м / услуга; или ввод)
        d. Кол-во    (число > 0)
        e. Цена за ед. (число ≥ 0, две decimals)
     → после позиции:  [➕ Добавить ещё]  /  [✅ Готово]
  5. ПРЕДПРОСМОТР: бот присылает распознанную таблицу текстом + Итого.
        [✅ Сгенерировать PDF]  /  [✏️ Начать заново]
  6. Генерация PDF → отправка файлом в чат. Запись в БД.
```

**Валидация:** кол-во — положительное число; цена — неотрицательное, парсинг
допускает `350`, `350,00`, `350.00`, пробелы-разделители тысяч. При ошибке —
переспрос того же поля, без потери введённого.

## 5. Данные

### 5.1 CompanyProfile (расширение существующей модели)
Добавить поля (nullable, дефолты):
- `kp_number_prefix` (String) — напр. `ИПХИС`
- `kp_counter` (Integer, default 0) — автоинкремент номера
- `kp_default_validity_days` (Integer, default 15)
- `kp_default_payment_terms` (Text)
- `kp_default_delivery_terms` (Text)
- `kp_signer_name` (String) — ФИО под подписью (если отличается от director_name)

### 5.2 Новая модель `CommercialProposal`
- `id`, `user_id` (FK sniper_users)
- `number` (String) — итоговый номер (`ИПХИС-26064`)
- `recipient_kuda`, `recipient_komu`, `recipient_tel` (nullable)
- `vat_mode` (String: `none` | `vat20`)
- `delivery_time` (String)
- `items` (JSON) — список `{name, proposed_name, unit, qty, price, sum, delivery}`.
  В MVP `delivery` каждой строки = общий `delivery_time` (per-row override — v2).
- `total` (Numeric), `vat_amount` (Numeric, nullable)
- `created_at`

(Файл PDF в MVP не храним — см. §7; при необходимости реэкспорт из `items`.)

Альтернатива: переиспользовать `GeneratedDocument` с `doc_type='proposal_kp'`.
**Решение:** отдельная модель `CommercialProposal` — у КП своя структура (позиции,
НДС, получатель), которую неудобно ложить в generic `GeneratedDocument`.

## 6. Рендеринг PDF

- Модуль `tender_sniper/kp_generator/` (отдельно от `document_generator/`):
  - `models.py` — dataclass `KPData`, `KPItem` (чистые данные, без БД).
  - `renderer.py` — `render_kp_pdf(kp_data) -> bytes` через Jinja2-шаблон + WeasyPrint.
  - `templates/kp.html` + `kp.css` — вёрстка бланка 1-в-1 с образцом.
  - `service.py` — сборка `KPData` из `CompanyProfile` + ввода, расчёт сумм/НДС,
    инкремент номера, сохранение `CommercialProposal`.
- Числа форматируются по-русски: `3 968 150,00` (пробел-тысячи, запятая-дроби).
- Инфраструктура: добавить в `Dockerfile` системные пакеты WeasyPrint
  (`libpango-1.0-0`, `libpangocairo-1.0-0`, `libgdk-pixbuf2.0-0`, шрифты с кириллицей,
  напр. `fonts-dejavu`), в `requirements.txt` — `weasyprint`.

## 7. Обработка ошибок

- Профиль не заполнен → мягкий отказ + ссылка на `/profile`, без падения.
- Ошибка рендеринга PDF → лог + сообщение «Не удалось собрать PDF, попробуйте ещё
  раз», состояние FSM сохраняется (данные не теряются).
- Хранение PDF: MVP — **не храним файл на диске** (Railway эфемерна), отдаём инлайн
  в чат; в БД пишем метаданные (`CommercialProposal`) для истории/номера. Если позже
  нужен реэкспорт — генерируем заново из сохранённых `items`.

## 8. Тестирование

- Unit: расчёт сумм и итога; НДС-разбивка (none/vat20); формат чисел; инкремент
  номера; парсинг цены/кол-ва (`350`, `350,00`, `1 000`).
- Рендер: `render_kp_pdf` на фикстуре → PDF непустой, содержит номер/итог
  (проверка через извлечение текста).
- FSM: happy-path (2 позиции → предпросмотр → PDF), «Пропустить получателя»,
  ошибка валидации кол-ва/цены с переспросом.

## 9. Вне скоупа (YAGNI сейчас)

- AI-парсинг позиций из свободного текста.
- Привязка КП к карточке тендера / автозаполнение получателя из заказчика.
- Веб-версия в кабинете.
- Автоприкрепление PDF к сделке Bitrix.
- Логотип/печать/факсимиле картинкой.

Эти пункты — кандидаты на v2, легко достраиваются поверх `KPData`/`renderer`.

## 10. Связанные будущие идеи (запаркованы)

Дизайн осознанно оставляет `kp_generator` автономным, чтобы позже он стал кусочком
пайплайна «двойной канбан закупщики↔тендерщики» (см. память
`idea_kanban_split_buyers_bidders`): КП прикладывается к карточке тендерщика.
